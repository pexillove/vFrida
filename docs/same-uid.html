vFrida · PROC

如何让同 UID 应用计数保持为 1

客端和宿主进程共用一个内核 uid。检测方数这个 uid 下有几个包名时，本来会得到 2。 vFrida 把同 uid 宿主进程的 cmdline 也显示成客端包名，去重之后只剩 1。

目录 检测在数什么 为什么会得到 2 绕过 两条通道 故意不动的部分

检测在数什么

结果写在 a118。普通应用这个值是 1：自己的 uid 下面只有自己这一个包，并且 /data/data/<包名> 存在。

阶段一：cgroup 只是闸门

读取 /proc/self/cgroup。在全文里取最后一次出现的 uid_ 之后、最后一次出现的 /pid_ 之前的数字，例如 0::/uid_10403/pid_7454 取出 10403，再拼出用户名 u0_a + (数字 - 10000)。

文件打不开、截出来的不是纯数字、用户名为空，或者后面 /proc 列不出来，都直接把 a118 写成 0。这个用户名不再参加后面的筛选。

阶段二：同 uid 包名去重

1
myUid = Process.myUid()，准备一个空的 HashSet。
2
遍历 new File("/proc").listFiles()。不是目录，或者目录名不是纯数字 pid，就看下一条。
3
读 /proc/<pid>/status 的 Uid: 行。第 2 列解析成功并且等于 myUid，才继续。
4
读 /proc/<pid>/cmdline。取第一个 \0 之前，再取第一个 : 之前，得到包名。空字符串丢掉。
5
/data/data/<包名> 存在，才 HashSet.add(包名)。同一个包的多个进程只计一次。
6
循环结束，a118 = HashSet.size()。
阶段一失败和阶段二数出 0 都是 a118 = 0。正常手机上能解析 cgroup 的应用得到的是 1，不是 0。绕过的目标是把计数留在 1，而不是把闸门弄坏。

为什么 vFrida 里会得到 2

客端进程的内核 uid 就是宿主 uid。OsStub.getuid 也把 Process.myUid() 返回成这个宿主 uid，于是 status 里的 Uid: 和 myUid 对得上，这些进程都会进入集合。

内核里的进程名仍是宿主包：

进程内核 cmdline冒号前的包名
宿主主进程com.android.vfridacom.android.vfrida
:blackcom.android.vfrida:blackcom.android.vfrida
桩进程com.android.vfrida:p0com.android.vfrida
当前客端同样是 com.android.vfrida:pN见下一行

当前客端自己的 /proc/<pid>/cmdline 和 /proc/self/cmdline 已经指到 v0/proc/<bpid>/cmdline。这个文件在进程拉起时写成客端的 processName，例如 com.example.app 或 com.example.app:push。检测方取冒号前，得到客端包名。/data/data/com.example.app 又被 IO 重定向到虚拟数据目录，exists() 为真。

于是集合里有两个包：

  • com.android.vfrida：其它同 uid 进程的真实 cmdline，/data/data/com.android.vfrida 在磁盘上存在
  • com.example.app：当前进程被换过的 cmdline，虚拟数据目录也存在

a118 变成 2。多开几个客端也不会再增加，因为它们的内核 cmdline 去掉冒号后仍是宿主包，已经被去重。

绕过

不改 cgroup，不改 status 里的 uid，也不把宿主的 /data/data 藏起来。只改检测方读到的 cmdline：凡是内核 uid 等于宿主 uid、并且内核 cmdline 的包名就是宿主包的进程，都打开客端那份 cmdline 文件。

判断写在 IORedirect.siblingCmdline：

  1. 路径必须是 /proc/<数字>/cmdline，且不是当前进程。当前进程仍走原来的 /proc/self 映射。
  2. 读 /proc/<pid>/status 的第一组 uid，必须等于 BbCore.getHostUid()。
  3. 读内核 cmdline，取 \0 之前。必须等于宿主包名，或者以 宿主包名: 开头。
  4. 客端 cmdline 文件存在，才把这次打开指过去。

读 status 和内核 cmdline 时要看真实文件。这两次打开套在 sProcBypass 里，redirectPath 直接返回原路径，避免用「已经换成客端包名」的结果来决定要不要换。

换完之后，主进程、:black、:pN 和当前客端取出的包名都是 com.example.app。/data/data/com.example.app 存在。集合大小是 1。

zygote 以及其它 uid 的进程保持内核 cmdline。找 zygote pid 时仍然能读到 zygote64。

两条通道

enableRedirect 时，aliasSiblingCmdlines 把当时已经存在的同 uid 宿主进程写进规则表。键是 /proc/<pid>/cmdline，值是客端 cmdline 文件。这张表同时交给 Java 的 Trie 和 BNative.setupRedirect，所以 libc 的路径 hook 和可选的 seccomp 重写也能命中这些已经在跑的 pid。

规则装上之后才出现的宿主进程，不在这张静态表里。redirectPath 在查 Trie 之前再跑一次 siblingCmdline。Java 的 new File、FileReader 走 libcore.io.Os，OsStub 会把以 / 开头的参数送进这里，因此这种晚出现的 pid 对 Java 检测仍然显示成客端包名。

晚出现的 pid 如果被未经过 Os 的原始 svc 打开，静态表里没有它，seccomp 那条规则也不会临时补上。图里的检测使用 java.io.File，走的是 Os。

故意不动的部分

检测步骤vFrida 的处理
/proc/self/cgroup 里的 uid_ / /pid_保持内核内容。阶段一仍能通过。
status 的 Uid:保持宿主 uid，与 Process.myUid() 一致。只伪造当前进程的 PPid。
/data/data/com.android.vfrida仍在。计数不再取出这个包名，所以它在不在都不增加 a118。
当前进程自己的 cmdline仍是原有的 /proc/self/cmdline 映射，不在同级扫描里再改一次。

路径重定向的其余规则见 IO 重定向。

依据 IORedirect.siblingCmdline、aliasSiblingCmdlines 和 OsStub。
