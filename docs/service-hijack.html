为什么要劫持

虚拟应用没有自己的 system_server。Activity、Service、广播、包查询仍然走本机的 ActivityManager 和 PackageManager。如果不改调用路径，系统看到的是宿主包名和宿主 uid，访客自己的组件也进不了桩进程。

vFrida 在访客进程（以及 :black 服务进程）里做两件事。一件是把系统服务的 Binder 换成代理，让 startActivity、getPackageInfo 这类调用先到 Java 代理。另一件是替换进程里框架已经拿住的对象：主线程 Handler 的回调、Instrumentation、libcore.io.Libcore.os。前者拦跨进程服务，后者拦本进程里框架自己走的入口。

系统服务劫持

换掉 ServiceManager 缓存或框架单例里的 Binder / 接口，按方法名改写参数或转给 BActivityManager、BPackageManager。

系统劫持

换掉 ActivityThread.mH 的 Callback、mInstrumentation 和 Libcore.os，在启动活动和打开文件之前插入沙箱逻辑。

两层对象

所有注入器都实现 IInjector：inject() 装上代理，isBadEnv() 判断代理是不是还在原位。Binder 服务和普通 Java 对象共用同一套动态代理，差别只在「代理最后写回哪里」。

ClassInvocationStub.inject 先 getWho() 取出真对象，再用 Proxy.newProxyInstance 包住它实现的全部接口。onlyProxy 为假时调用子类的 inject(base, proxy)，把代理写回框架。接着扫描内部类上的 @ProxyMethod / @ProxyMethods，以及类上 @ScanClass 指向的兄弟类，把每个内部类实例登记成 MethodHook。

何时装上

BbCore.doAttachBaseContext 按进程名区分主进程、Server（:black）和访客。三类进程都会走到 HookManager.init()，但登记表只在 Server 和访客里填充。主进程不替换系统服务。

1
登记

addInjector 按类名放进 mInjectors。ActivityManager、PackageManager、电话、通知、窗口、定位这些始终登记；权限、存储统计、Job、指纹等按 BuildCompat 的 API 级别补上。

2
注入

injectAll 逐个调用 inject()。ActivityManager、PackageManager、WebView、ContentProvider 失败时，若 isBadEnv() 仍为真会再试一次。

3
复查

之后 checkEnv / checkAll 发现代理被框架换回去，就再 inject() 一次。

系统服务劫持

应用拿系统服务，走的是 ServiceManager.getService(name)。这个方法先查进程内静态表 sCache。命中就不再向 servicemanager 要 Binder。BinderInvocationStub.replaceSystemService 放进这张表的是只实现 IBinder 的动态代理。公开接口生成的类名是 $Proxy 加数字，例如 $Proxy0。

代理把 transact、pingBinder、linkToDeath 转给桩，桩再转给原来的系统 Binder。queryLocalInterface 仍返回接口上的动态代理，所以 asInterface 在本进程拿到的是带方法钩子的对象，而不会再打一次 Binder。

包管理：缓存和已缓存的接口一起换

IPackageManagerProxy 继承 BinderInvocationStub，构造时拿 ActivityThread.sPackageManager().asBinder() 当底座。注入时做三处替换：

  1. ActivityThread.sPackageManager 改成代理，框架里已经取出的接口不再指向系统。
  2. replaceSystemService("package")，后来的 getService("package") 也进桩。
  3. 系统 Context 上的 ApplicationPackageManager.mPM 改成同一代理，并关掉 ApplicationInfo 缓存，避免旧的包信息留在框架里。

方法钩子里，已安装到沙箱的包名查询转到 BPackageManager；需要过系统权限检查的调用，由 PkgMethodProxy / ValueMethodProxy 把包名、uid 改回宿主再交给原来的 mBase。

活动管理：换单例里的实例

ActivityManager 在 Oreo 之后是 ActivityManager.IActivityManagerSingleton，更早是 ActivityManagerNative.gDefault。两者都是 Singleton。IActivityManagerProxy.getWho 取出 Singleton.get() 的当前实例做代理底座；inject 把 mInstance 写成代理。之后 ActivityManager.getService() 直接返回这个代理。

isBadEnv 比较「当前单例实例」和「我们装上的代理」。框架若重新 get() 出了新的系统接口，复查时会再注入。@ScanClass(ActivityManagerCommonProxy.class) 把启动活动、绑定服务、发广播等公共改写放在另一个类的内部类里，注入时一并登记。

一次 startActivity 的典型去向：代理认出桩 Intent 里的 ProxyActivityRecord，把目标改成宿主清单里的桩 Activity，真正的组件信息留给 HCallbackProxy 在主线程还原；或者把调用转到 BActivityManager，由 :black 里的 BActivityManagerService 决定进哪个槽位进程。代理自己的 invoke 若碰到 SecurityException，按方法名前缀返回空或 0，避免访客因为宿主权限直接崩溃。

其余服务

电话、订阅、通知、闹钟、窗口、用户、定位、账号、存储、网络、AppOps、WebView、小米服务都是同一模式：StubHelper.getServiceInterface 用 BlackReflection 生成的 Stub 或系统 asInterface 取出接口，replaceSystemService 换掉对应的服务名（如 phone、window、location）。MethodHook.isEnable 默认只在访客进程生效，Server 进程里装上的代理多数方法会直接转到原来的系统对象。

一次调用怎么分发

ClassInvocationStub.invoke 只用方法名查表，不看参数签名。没有钩子，或钩子 isEnable() 为假，就 method.invoke(mBase, args)。有钩子时顺序是：

  1. beforeHook：返回非 null 则直接作为结果，不再调用原方法。
  2. hook：子类实现。常见写法是改 args 后 method.invoke(who, args)，或改调 BActivityManager / BPackageManager。
  3. afterHook：改返回值，默认原样返回。
同名重载会撞在同一条钩子上。需要区分时，钩子自己看 Method 的参数类型。

系统劫持

有些路径不经过 ServiceManager。系统在本进程里已经握住 Handler、Instrumentation 和 Os。这些要单独换。

主线程消息：HCallbackProxy

ActivityThread 的 mH 是主线程 Handler。注入时读出原来的 mCallback，再把 mCallback 设成 HCallbackProxy。回调返回 false 时，消息仍会进 ActivityThread.H.handleMessage，所以未处理的消息保持原行为。

Pie 及以后，启动活动的消息是 EXECUTE_TRANSACTION，更早是 LAUNCH_ACTIVITY。handleLaunchActivity 从 ClientTransaction 里取出 LaunchActivityItem（或旧的 ActivityClientRecord），读 Intent：

  • 进程还没有 AppConfig：向 BActivityManager 要求按包名和进程名重启，把启动 Intent 写回消息，并把这条消息插到队列头，返回 true 吃掉当前这次，等进程准备好再执行。
  • 线程还没 bindApplication：用 ActivityInfo 里的包名和进程名绑定访客，换上真实的 Application、ClassLoader 和重定向规则，同样把消息重新入队。
  • 已经绑定：把桩 Activity 的 Intent 还原成访客真实组件，后续 H.handleMessage 创建的就是访客 Activity。

CREATE_SERVICE 走 handleCreateService。桩进程里若要创建的不是本槽位的 ProxyService / ProxyJobService，就改走 BActivityManager.startService。处理期间用 AtomicBoolean 挡住重入。原来的 callback 在 vFrida 不接管的消息上继续被调用。

Instrumentation：AppInstrumentation

活动真正 new 出来、调用 callActivityOnCreate，走的是 ActivityThread.mInstrumentation。绑定应用时 BActivityThread 调用 AppInstrumentation.inject：记下当前 Instrumentation 作为 mBaseInstrumentation，再把 mInstrumentation 设成自己。BaseInstrumentationDelegate 把未覆盖的方法转给原来的对象。

覆盖点集中在生命周期：创建活动前确认 ClassLoader 和主题，callActivityOnCreate 前后接上沙箱的 Activity 记录。若当前 Instrumentation 已经是 AppInstrumentation，或某个包装类的字段里能找到它，inject 直接返回，避免套两层。

文件：OsStub

Java 的 java.io / android.system.Os 最终调用 libcore.io.Libcore.os。OsStub 代理这个对象并写回 Libcore.os。invoke 扫描参数里以 / 开头的字符串，交给 IORedirect 换成沙箱路径，再调用原来的 os。这是 Java 层的路径劫持；native 的 openat 和可选的 seccomp SVC 兜底在另一条链上，见 路径重定向 和 路径类 SVC。

坏环境

框架会在某些时机重新取出系统服务，把单例或 Handler 回调换回去。isBadEnv 就是在比较「现在坐在那个字段里的对象」和「我们装上的代理」。HCallbackProxy 发现 mCallback != this 为坏环境；IActivityManagerProxy 发现单例 get() 不再是代理为坏环境；OsStub 发现 Libcore.os 不是代理为坏环境。HookManager.checkEnv 只重装这一个，checkAll 扫整张表。

如何检测

isBadEnv 检查的是代理还在不在，用来发现框架把钩子换掉了。下面是反过来：从进程里已有的对象判断这三种替换是否已经装上。三种留下的类型不同，不能用同一种比较。

BinderInvocationStub

一项常见检查是对 location、phone、clipboard 调用 ServiceManager.getService，看返回对象的类名。正常是简单类名 BinderProxy，或者类名以 $Proxy、$Proxy 加数字结尾。两个都不是才算异常。

写进 sCache 的动态代理类名是 $ProxyN，这一项保持正常。clipboard 没有替换，仍是 BinderProxy。接口上的代理类名同样以 $Proxy 结尾。方法钩子在接口代理的 InvocationHandler 上，那个对象的类才在 com.android.bb.hook。

  • queryLocalInterface 返回接口代理。远端 BinderProxy 在应用进程里通常返回 null，接口要靠 asInterface 再包一层。
  • transact 仍转给原来的系统 Binder，getInterfaceDescriptor 也还是系统描述符。描述符对得上，不能说明没被换。

ClassInvocationStub

这里换的不是 Binder 缓存，而是框架已经 asInterface 或 Singleton.get() 拿到的 Java 对象。代理类是 java.lang.reflect.Proxy 生成的 $ProxyN，InvocationHandler 是对应的 Stub。

  • ActivityManager.getService()（Oreo 起是 IActivityManagerSingleton 的 mInstance）上调用 Proxy.isProxyClass。为真则活动管理已被 IActivityManagerProxy 包住。Proxy.getInvocationHandler 的类名是 IActivityManagerProxy。
  • libcore.io.Libcore.os 正常是 BlockGuardOs 或 Linux。变成 $Proxy 且 handler 是 OsStub，就是路径劫持。
  • 调用栈里出现 ClassInvocationStub.invoke，说明这次调用经过了方法表，而不是直接进系统实现。

直接实现 IInjector

这五个不是 $Proxy，检测就是看字段里坐着的具体类。

字段装上之后的类
ActivityThread.mH.mCallbackHCallbackProxy
ActivityThread.mInstrumentationAppInstrumentation。外层若再包一层，要沿字段往下找，AppInstrumentation.checkInstrumentation 就是这么做的
Runtime.exit 是否被拦住AntiVirtualDetectProxy 只置了 sInstalled，当前没有真正换方法
网络权限兼容、资源管理NetworkPermissionCompat、BResourcesManager 没有替换一个全局单例，看 HookManager 的 mInjectors 里有没有这两个类

sCache 里的 Binder 现在和普通动态代理同一类名。要区分，得再看 queryLocalInterface 返回对象的 InvocationHandler 是不是桩。mH.mCallback 和 mInstrumentation 的类名仍是 com.android.bb.hook。类名在宿主包的访客进程里出现，就是这套劫持。
